# ADR 0034: Wire the Terminal Command Catalog

## Status

Accepted on 2026-08-16.

## Context

Continuing "Pass N+1a" from `docs/server-implementation-pass.md` (real-network fallback for `curl`/`nmap`/`cat`, extending the pattern `ping` already proved end-to-end per ADR 0028), research to confirm `ping`'s real-network fallback actually worked when launched for real — not just under direct unit-test construction — surfaced a foundational gap that blocked the pass entirely. The user confirmed it needed fixing before anything else: *"on doit câbler ces applications pour pouvoir les tester"* (we need to wire up these apps so we can test them).

Three separate, compounding gaps, found by reading the actual composition-root code rather than trusting "proven end-to-end" language in prior ADRs/roadmap text:

1. **None of the 28 `Apps/Commands/*` projects (curl, nmap, ping, cat, ls, echo, mkdir, grep, ps, kill, nano, ...) were referenced by `OS/HackerOs.Ecosystem/HackerOs.Ecosystem.csproj`** — no `ProjectReference`, no `EmbeddedResource` manifest entry, no `BlazorWebAssemblyLazyLoad` entry (only the 12 `Apps/System/*` window apps were listed in all three). Confirmed live: opening the WASM test harness's Terminal and running `help` showed `Built-in commands: clear, cd, pwd, help` / `Catalog commands: ` (empty). `BuildKnownLazyApps.Catalog` (`OS/HackerOs.Ecosystem/BuildKnownLazyApps.cs`) — the single source every host (WASM, `test/test`, `Server/HackerOs.Server`) reuses — is built purely from this `.csproj`'s embedded resources, and `BuildKnownLazyAssemblies.Names`/the whole lazy-loading pipeline (`BuildKnownAssemblyLoaderRegistry`, `BuildKnownLazyAppDescriptorRegistry`) derive automatically from whatever manifests that catalog contains. So this is the one place to fix for all three hosts at once, mirroring the existing pattern for the 12 working apps exactly.
2. **`AppLifecycleOrchestrator.RunTerminalAsync`/`StartService` constructed every terminal/service app via `Activator.CreateInstance(descriptor.EntryPointType, descriptor.Manifest)`** — a single-argument call. Commands whose constructor takes only `AppManifest` (cat, ls, echo, pwd, cd, mkdir, ...) happened to work; `PingCommand(AppManifest, ISimulatedNetworkService, IServerConnectionService, IProxyClient)` and `CurlCommand`/`NmapCommand(AppManifest, ISimulatedNetworkService)` did not. Every "proven end-to-end" claim about `ping`'s real-network fallback (ADR 0028, the roadmap doc) referred to direct construction in `Wave4NetworkTests.cs`, never an actual launch through the orchestrator. In practice this did **not** crash the app or throw unhandled — `LaunchAsync`'s existing `catch (Exception ex)` around the terminal/service dispatch caught the resulting `MissingMethodException` and reported it as `AppLaunchStatus.EntryPointFault` with a cryptic reflection error message. Confirmed and characterized by a new regression test (see Implementation below) before fixing it.
3. **`ISimulatedNetworkService` (and its `ISimulatedDns`/`ISimulatedWebsiteRegistry` dependencies) were registered nowhere in `EcosystemServiceCollectionExtensions.cs`.** Even after fixing (1) and (2), `curl`/`nmap`/`ping`'s simulated-network lookup would fail to resolve from DI. There was also no production seed data (which hosts exist, what they serve) anywhere — the "Game domain" module (`Game/HackerOs.Game.Core/`) ADR 0023 scoped this content into contains exactly one file (`InMemoryGameDomainGateway.cs`) and no host/website content at all. Authoring a full simulated-internet content pack is its own, much larger, separate undertaking (game design, not plumbing) and stays explicitly out of scope here.

## Decision

### 1. Wire 24 of the 28 `Apps/Commands/*` projects into the catalog

Added `ProjectReference` + `EmbeddedResource` (`Link="Manifests\{app-id}.json"`) + `BlazorWebAssemblyLazyLoad` entries to `HackerOs.Ecosystem.csproj` for every command project **except** `Cd`, `Pwd`, `Clear`, `Help`. `TerminalWindow.razor` intercepts those exact command names before catalog resolution ever runs (hardcoded built-ins — confirmed by reading the dispatch code: `if (cmd == "clear") { ...; return; }` etc., unconditionally, before `_resolver.Resolve(cmd, args)`). Wiring their catalog counterparts would make them permanently unreachable dead entries, and would misleadingly duplicate them in both the "Built-in" and "Catalog" lists in `help`'s own output. This is a deliberate exclusion, recorded here rather than an oversight.

### 2. `AppLifecycleOrchestrator` constructs terminal/service apps through DI when a service provider is supplied

Added an optional, trailing `IServiceProvider? services = null` constructor parameter (matching the existing `eventBus`/`descriptorLoader`/`catalogRepository` optional-parameter convention — no existing call site breaks). A new private `CreateAppInstance(AppDescriptor descriptor)` helper uses `ActivatorUtilities.CreateInstance(_services, descriptor.EntryPointType, descriptor.Manifest)` when `_services` is supplied, falling back to the original `Activator.CreateInstance(descriptor.EntryPointType, descriptor.Manifest)` when it isn't — preserving exact prior behavior for tests that only construct manifest-only commands and don't need DI. Both `RunTerminalAsync` and `StartService` now call this one helper instead of duplicating the construction logic.

### 3. Register the simulated network with a small, explicitly-labeled smoke-test seed

`SmokeTestNetworkSeed` (`Platform/HackerOs.Platform.Core/Network/SmokeTestNetworkSeed.cs`) provides two `SimulatedHost` entries (`example.hackeros`, `empty.hackeros`) and one minimal `ISimulatedWebsiteController`. Every hostname uses the `.hackeros` suffix the server-side proxy already treats as simulated-only (`ProxyService`'s blocked-suffix list, ADR 0028) — unambiguous that these are smoke-test fixtures, never real network destinations. `EcosystemServiceCollectionExtensions.cs` registers `ISimulatedWebsiteRegistry`/`ISimulatedNetworkService` from this seed. This is explicitly **not** an attempt at the "Game domain" content pack ADR 0023 scoped separately — it's the minimum needed to prove `curl`/`ping`/`nmap`'s *simulated* path actually works end-to-end now that the commands are launchable at all.

### 4. Fix five commands' incomplete capability declarations, found during live verification

Live-verifying the plan's own success criteria (`help`, `curl`/`ping`/`nmap` against the seed hosts, basic `ls`/`cat`/`mkdir`) in a real browser session surfaced a fourth gap, orthogonal to the three above: `mkdir`, `touch`, `rm`, and `chmod` each call `FileSystem.StatAsync` (a read operation, resolving to the `filesystem.user-home.read` capability) on their target's parent before mutating it, but their manifests declared only `filesystem.user-home.write`. Under the deny-by-default `CapabilityGrantRepository` (`Platform/HackerOs.Platform.Core/Policy/CapabilityGrantRepository.cs`), `CleanProfileCapabilityGrantSeeder` only ever grants capabilities a manifest *declares* — so the missing read declaration meant the parent stat was silently denied, and each command's generic error handling reported it as `No such file or directory` rather than a permission problem. Separately, `alias`'s C# `StaticManifest` already declared both read and write, but its `app.manifest.json` — the actual embedded resource `BuildKnownLazyApps.Catalog` loads, not the C# constant — still had `"capabilities": []`, a stale JSON/C# divergence. None of these five commands had ever been launched in a real session before this pass, so none of this was previously observable. Fixed by adding the missing `filesystem.user-home.read` declaration to both the C# `StaticManifest` and the `app.manifest.json` for `Mkdir`, `Touch`, `Rm`, and `Chmod`, and by fixing `Alias`'s `app.manifest.json` to match its already-correct C# declaration — matching the pattern `Cp`/`Mv` already had right. Verified live: `mkdir`, `touch`, `chmod`, `rm`, and `alias` all now succeed against a freshly created profile.

### 5. Stop here — defer real-network `curl -I` wiring to a follow-up pass

The original "Pass N+1a" scope (wiring `curl -I` into the real proxy bridge, matching `ping`'s `IProxyClient` pattern) depends on all four fixes above. Bundling it into the same change would make an already-large, foundational fix harder to review and verify. The next pass resumes exactly where the original roadmap left off: `curl -I` real-network fallback (small, no server changes needed), with full-body `curl`/`cat` and real `nmap` scanning remaining explicitly deferred (blocked on the separate, larger proxy body-transfer and TCP-scan gaps already documented in `docs/server-implementation-pass.md`'s open questions).

## Consequences

- The terminal is now actually usable end-to-end with its full command suite (minus the four dead-by-design entries) across all three hosts — a real, previously-invisible gap is closed, not just curl/nmap/ping/cat as originally scoped.
- `AppLifecycleOrchestrator`'s terminal/service construction is now DI-aware in general — any future command needing injected services benefits automatically, not just the three that motivated this fix.
- `curl`/`nmap`/`ping` are now exercisable against `example.hackeros`/`empty.hackeros` in simulation, but the simulated content is intentionally minimal — it is not, and should not be mistaken for, the "Game domain" content pack.
- `mkdir`/`touch`/`rm`/`chmod`/`alias` now actually work end-to-end rather than failing on their first parent-directory stat — a second, independent class of previously-invisible defect this pass's live verification step exists specifically to catch.
- Real-network fallback for `curl -I` (the original Pass N+1a scope) is deferred to the very next pass, now that its prerequisites are in place and verified.
- A separate, still-open defect was found and left unfixed (see `docs/server-implementation-pass.md`'s open questions): `cat` fails to read a file `touch` just created (`FileSystem.ReadAsync` returns not-found even though the same path's `StatAsync`/`EnumerateAsync` succeed), suggesting the VFS provider treats an empty/never-written file's content as absent rather than zero-length. This looks like a `FileSystemService`/provider-level bug orthogonal to catalog wiring or capability declarations, and needs its own investigation.
