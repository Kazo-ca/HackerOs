# ADR 0173: automatic release from the version file

## Status

Accepted on 2026-10-26 at Benoit's request ("change just 1 file and have every
assembly change version; when the version changes on `main`, deploy the NuGet
packages and the rest to the repository's releases"). Replaces the "never
nuget.org" rule of [ADR 0098](0098-sdk-versions-packages-and-manifest-checks.md) §2;
the rest of ADR 0098 (single version, packages, local feed) still holds.

## Context

- `wasm2/HackerOs/build/Versions.props` (`HackerOsVersion`) already gives its
  version to every project (ADR 0098 §1): assemblies, 42 `HackerOs.*` packages,
  templates, generated manifests, `HackerOsSdk.Version` shown by the OS.
- Releasing stayed manual: no tag, no GitHub Release, packages only produced
  into `artifacts/local-nupkg`.
- Only one place still hard-coded the number: the `PublishedPagesTests` test of
  `HackerOs.Pwa.E2E.Tests` (`"2.0.3"`).

## Decision

1. **One file**: releasing a version means changing `HackerOsVersion` in
   `build/Versions.props` and merging into `main`. No code or test repeats the
   number: the PWA test reads `HackerOsVersion` through an `AssemblyMetadata`
   of its project. The generated manifests (tracked by git for review) are
   rewritten by the build; committing them with the version bump is advised,
   not required.
2. **`Release HackerOS` workflow** (`.github/workflows/release.yml`), started
   when **Verify HackerOS WASM** succeeds on a push to `main`: it reads the
   version of the verified commit and, if the `v<version>` tag does not exist,
   - packs through `build/pack-local.sh --ci` (`ContinuousIntegrationBuild=true`);
   - keeps only the `HackerOs.*.<version>.nupkg` and `.snupkg` files (never a
     `Contoso.*` compatibility app);
   - publishes the WASM site and zips it (`hackeros-wasm-<version>.zip`);
   - pushes the packages to nuget.org (`--skip-duplicate`);
   - creates the tag and the GitHub Release **last** (notes generated by
     GitHub, packages and zip attached; pre-release when the version has a
     `-…` suffix).
   The tag is the "already released" marker: a commit whose version is already
   tagged releases nothing. A failure before the tag is retried by rerunning
   the workflow.
3. **nuget.org authentication**: *Trusted Publishing* (OIDC, `NuGet/login@v1`,
   key valid for one hour) when the `NUGET_USER` repository variable exists;
   otherwise the `NUGET_API_KEY` secret; otherwise no push, a warning, and the
   Release is still created.
4. **Republishing**: run by hand on `main` with the `republish` option, the
   workflow takes the tag of the current version, packs again and pushes to
   nuget.org (for a version released before NuGet was set up).
5. The number still follows SemVer (ADR 0019, ADR 0114);
   `build/tools/ship-public-api.sh` folds `PublicAPI.Unshipped.txt` into
   `Shipped` for a minor or major release, in the same PR as the version bump.

## Consequences

- A PR that does not change the version releases nothing; a PR that changes it
  releases once, after a green verification of `main`.
- The `HackerOs.*` IDs become public on nuget.org; the local feed stays
  available to try an unreleased version.
- The workflow is never started by a pull request or by a `*/base` branch.

## Rejected options

- **Version computed from tags** (MinVer, GitVersion): the version would no
  longer live in a file, and a manual tag would become the release action.
- **Triggering on a `Versions.props` change in the push**: a verification
  cancelled by a following push would lose the release; the "tag missing" test
  picks it up at the next commit.
- **Releasing from the verification workflow**: its concurrency group cancels
  running runs, which could cut a NuGet push in half.
